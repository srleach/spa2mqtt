    Jacuzzi plain protocol (unencrypted boards, via ProLink)¶

    This document describes the protocol of unencrypted Jacuzzi boards as far as one tub shows it: a Jacuzzi J345 (J-300 series) reached through the Jacuzzi ProLink module. It is the reference for definitions/jacuzzi_j345.yaml and for the bridge's direct bus mode. The J235 does not use these frames: see the wire protocol for the encrypted boards.

    Ground truth rule. Where sources disagree, the captured dumps win. Statuses mean the same as in the wire protocol, with this tub in place of the J235. Nobody on the project has this tub, so no claim here was checked by the project against the tub itself. The checks are the owner's captures, pyjacuzzi's code, and the tub's recorded reaction to commands that pyjacuzzi sent.

    Index convention. p[n] is payload byte n, counted from 0 at the first byte after TYPE. A field's byte: n in the definition uses the same index. pyjacuzzi and jackbrown1993 index the whole frame: their data[k] is p[k-5].

    1. Framing¶

    The frame is the same as on the encrypted boards (wire protocol §2):

     7E | LEN | ADDR | MID | TYPE | payload ... | CRC | 7E
    Claim Status Evidence
    LEN = total bytes − 2. CRC-8 (poly 0x07, init 0x02, xorout 0x02) over LEN through the last payload byte. Confirmed All 2 133 frames in S, D, X1–X3 decode with the existing decoder: 0 CRC errors, 0 resyncs
    The payload is plaintext: no per-frame key, no key stream. Confirmed Identical states give identical frames (D L6–L75 repeat one frame); S: a sent 20 5a appears as p[9] = 5a
    spa2mqtt.protocol needs no change for these frames. Confirmed Frame.encode() reproduces every captured frame, sent and received

    0x23 0xFF 0xAF board → all 28 Lights, about every 1.0 s Confirmed S: 19, D: 38, X3: 395

    0x19 0x0A 0xBF client → board 2 Panel request (PJ: primary filter cycle) Inferred S L3; PJ L1760–1762

    Each pump field is two bits wide, and only the values 0 and 2 were seen. The definition reads the high bit. A low speed (value 1), if a pump has one, would read as off.

    4. Lights 0x23 (28 payload bytes)¶

    Four 7-byte records. Record k is p[7k .. 7k+6]:

    Offset Field Status Evidence
    0 Mode: 00 off, 01–09 colours, 80 blend, ff blend paused Confirmed (record 0) Every 21 1f MM command gives mode MM in the next frame (§5). 80, ff from the topside: X3 L1354, L1376. PJ L1546
    1 Sub-mode: 02, then 04, only in blend Unknown X2 L19; X3 L1354, L1363
    2 Brightness, percent Confirmed 21 2f … LL gives LL (S L63 → L64 and following). The topside steps 64, 42, 21 (X2 L32, L45). PJ L1547
    3, 4, 5 Red, green, blue Confirmed Match the commanded colour (S L27–L55). PJ L1548–1550
    6 Tail: 00, or ff in an untouched record Unknown X1 L2

    The definition decodes record 0 only: light_mode, light_brightness, light_red, light_green, light_blue.

    • The topside changes record 0 only (X2, X3).
    • pyjacuzzi's 0x21 commands set all four records to the same values (S L27 onward).
    • D L5 shows record 0 off while records 1–3 still hold blue (mode 02, brightness 60), apparently left by an earlier remote command that is not in the captures: D predates S by about 13 hours. A brightness command of 0 clears all four (S L58).
    • Which lamps records 1–3 drive is unknown.

    Colours, with the RGB the tub reported at brightness 60:

    03 green 00 ff 00 PJ

    06 red ff 00 00 PJ

    5. Commands¶

    Every command is sent to ADDR 0x0A, MID 0xBF, in plaintext. These are the complete frames from S. Frame(0x0A, 0xBF, type, payload).encode() reproduces each one, and tests/test_plain_j345.py asserts that the bridge emits exactly these bytes.

    Command Frame S line (sent → seen) Tub's reaction
    Panel request 7e 07 0a bf 19 01 00 95 7e 3 → 4 Reply 7e 07 0a bf 1b 13 0c 1a 7e after 96 ms
    Set temperature 90 °F 7e 06 0a bf 20 5a 93 7e 8 → 9 p[9] 50 → 5a
    Set temperature 100 °F 7e 06 0a bf 20 64 29 7e 10 → 11 p[9] → 64; circulation pump starts
    Set temperature 101 °F 7e 06 0a bf 20 65 2e 7e 13 → 14 p[9] → 65
    Button, pump 1 7e 06 0a bf 17 04 9c 7e 22 → 23, 24 → 25 p[10] 02 → 0a → 02
    Button, pump 2 7e 06 0a bf 17 05 9b 7e 17 → 18, 20 → 21 p[10] 02 → 22 → 02
    Light colour MM 7e 0d 0a bf 21 1f MM 00 00 00 00 ff 00 CRC 7e below All four records show mode MM
    Light brightness LL 7e 0d 0a bf 21 2f 01 00 00 00 00 LL 00 CRC 7e below Brightness = LL; 00 turns every record off
    Colour MM CRC Sent on S line Brightness LL CRC Sent on S line
    01 white 77 26, 47 00 (off) f9 57, 78
    02 blue 11 29, 60 14 (20) fa 63
    03 green ce 32 28 (40) ff 66
    04 yellow dd 50 3c (60) fc 69
    05 orange 02 35 50 (80) f5 72
    06 red 64 38 64 (100) 58 75
    07 violet bb 41
    08 amber 42 54
    09 aqua 9d 44

    Notes:

    • All 26 sends took effect on the first attempt. The tub reacts within one status period (95–374 ms); light changes show within one lights period.
    • The 01 after 2f is not a mode: the mode stayed 02 (S L64).
    • The ff brightness in a colour command left the brightness at 60. Whether 60 is a default or the previous value is unknown.
    • PJ jacuzziui.py L482–500: the board refuses mode 0 (turn off with brightness 0) and refuses blend (80) as a direct command. PJ L487–499 enters blend by sending brightness 0 and then a non-zero brightness. So a non-zero brightness command sent while the lights are off is expected to start blend mode. In S every non-zero brightness (L63–L75) was sent while the mode was 02, so this is not proven on this tub.
    • PJ jacuzzi.py L394–397 doubles the set-temperature value when the tub is in Celsius (half degrees C in the same byte). No capture shows Celsius mode. The definition's requires: {celsius_mode: false} makes the bridge refuse the 0x20 command unless the last status frame has p[13] bit 0 clear.

    Not proven on this tub. spa2mqtt does not send any of these:

    • 0x17 codes 01 temp up, 02 temp down, 11 light, 12 colour, 0f UV, 1e menu (JB jacuzziRS485.py L100–107, another tub).
    • Set time (0x18), locks (0x1F), filter commands (0x1B/0x1C), module-ident request (0x04), 0x1A buttons (PJ only).
    • Any 0x20 value other than 5a, 64, 65. The definition offers 80–104 °F, the lowest and highest setpoints any capture shows (S L5, X3 L1241), with the same one-byte encoding. How the tub treats a value outside its own range is unknown, so the bridge never builds one.

    6. Transport: the ProLink module¶

    Claim Status Evidence
    The ProLink serves the bus as raw frames on TCP port 4257. Confirmed Every log of this tub; PJ ProlinkMessageParsing.txt L846, L919
    The ProLink has the fixed bus address 0x0A. Confirmed All 26 sent frames and the 0x1B reply in S; PJ L198–202
    The stream carries no clear-to-send and no channel traffic. The ProLink appears to arbitrate the bus itself. Confirmed (absence), Inferred (reason) D, X1–X3: 2 074 frames, all FF AF 16 or FF AF 23. The v1 logger printed every frame of every type
    A client may write a command at any time, with no wait for a poll. Inferred PJ balboa.py L210 opens a bare socket and sends on user action; S: 26 of 26 sends worked
    pyjacuzzi sends 0x19 01 00 13 ms after connecting. Confirmed S L2 → L3. Whether later commands depend on it is unknown: no capture has a command without it
    pyjacuzzi spaces repeated presses 1.0 s apart. Confirmed (source) PJ L703–707. The two closest sends in S are 1.96 s apart
    The ProLink may sleep while the tub is idle. Hypothesis PJ readme.md items 6–7. The bridge reconnects after 30 s of silence

    Corroboration for the missing clear-to-send: the owner reported that JB's project showed temperatures on this tub but could not change anything. JB waits for a clear-to-send on its channel (jacuzziRS485.py L200–205), which this stream never delivers.

    What is on the RS485 bus behind the ProLink is unknown. An EW11A or ESP32 wired to this board might see clear-to-send frames and need the channel claim of the encrypted boards. Nobody has tried, so the loader rejects a plain definition with bus.mode: claim.

    7. What spa2mqtt sends¶

    The definition selects bus.mode: direct (design §6). With transmit on:

    1. Nothing is sent at start-up or on connect.
    2. A command from Home Assistant is queued (at most 8; more are dropped with a warning). A number outside its range is refused, not clamped. A setpoint is refused unless the last status frame shows Fahrenheit.
    3. On the next status frame, the bridge sends the connection_check frame (0x19) if it has not sent it on this TCP connection. bus.hello in the definition names it; without that key it is never sent.
    4. Four status frames later (about 1.2 s) it sends the queued frame, and so on: one frame per four status frames.
    5. Nothing is retried. A reconnect drops the queue and re-arms the connection check.

    Every frame goes through BusWriter.send(), so SPA_TRANSMIT=false blocks all of it.

    8. Unknowns¶

    1. Whether the 0x19 connection check is needed before commands work.
    2. Whether the ProLink accepts more than one TCP client, or the official app at the same time.
    3. Whether a direct RS485 tap on this board needs the clear-to-send and channel-claim exchange.
    4. Water temperature (p[7]) and the second sensor (p[16]) against the topside display.
    5. The heater bit (p[11] bit 0) and p[11] bits 1, 2 and 4.
    6. p[5] (08 against 02), and the heat-mode and filter-mode fields PJ places there.
    7. Pump low speed, pump 3, blower, UV.
    8. The tub's handling of setpoints other than 90, 100 and 101 °F, and of out-of-range values.
    9. Celsius mode: p[13] bit 0 and any half-degree encoding.
    10. Light records 1–3, the tail and sub-mode bytes, the 1f/2f selector byte, and why pyjacuzzi's command writes four records while the topside writes one.
    11. Whether a non-zero brightness command sent while the lights are off starts blend mode (PJ jacuzziui.py L487–499 says so).
    12. The 0x1B reply 13 0c. PJ reads it as filter start hour 19 and duration 12 h. The hour equals the tub's clock hour at that moment, which may be a coincidence.
    13. p[8] (fa), p[17..18] (01 1c), p[21..24] (80 00 80 00), p[28..31] beyond "0 normal, 1 setpoint edit", and the CLEARRAY counter's fall from 364 to 0 in six days.
    14. Month and year: seen for May 2025 only.
